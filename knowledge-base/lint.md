# Lint — 知識ベースを検査する

Wiki の品質を定期的に検査し、重複・矛盾・孤立・根拠不足・陳腐化・Skill へ昇格すべき知識を発見する。

Lint の目的は、古い資料を削除することではない。

**知識ベース内の問題を発見し、修正・統合・再検討が必要な候補を提示すること**を目的とする。

Lint は原則として、問題を発見しただけで Wiki の意味を自動変更しない。

---

# 基本方針

Wiki が100ファイル以上あっても、すべてのファイル同士を総当たりで比較しない。

```text
全 Wiki
   ↓
機械的に検査
   ↓
疑わしい候補を絞る
   ↓
必要なファイルだけ読む
   ↓
意味的に検査
   ↓
Lint 結果を提示
```

100ファイルなら全組み合わせは、

```text
100 × 99 / 2 = 4950組
```

になる。

LLM に4950組を比較させない。

まず検索索引、タイトル、リンク、キーワード、summary などで候補を絞る。

---

# Lint の実行単位

Lint は次の3種類で実行できる。

## 1. 単一ファイル Lint

新規作成・更新した Pattern だけを検査する。

対象:

```text
1ファイル
```

主に確認するもの:

- 必須情報
- provenance
- 既存 Pattern との重複
- 既存知識との矛盾
- 他 Pattern からの到達性

Ingest 後に実行する軽量 Lint。

---

## 2. 差分 Lint

前回 Lint 後に変更された Wiki だけを中心に検査する。

対象:

```text
変更された Pattern
+
それと関連する既存 Pattern
```

日常運用ではこれを基本とする。

全 Wiki を毎回精査しない。

---

## 3. 全体 Lint

Wiki 全体を検査する。

定期的な棚卸しや、大きな構造変更後に行う。

100ファイル程度でも、次の段階に分けて処理する。

---

# 全体 Lint の手順

## Phase 1. ファイル一覧を取得する

Wiki 配下の Markdown を列挙する。

確認する情報:

- path
- ファイル名
- 更新日時
- title
- Pattern 種別
- Wiki 内リンク
- provenance
- 他 Pattern からの参照
- index.db の summary

この段階では本文をすべて LLM に読ませない。

---

# Phase 2. 構造 Lint

機械的に判定できる問題を先に検出する。

## 孤立ページ

他の Wiki ページから辿れないページを探す。

例:

```text
A.md
    ↓
B.md

C.md ← どこからもリンクされない
```

`C.md` を孤立候補とする。

ただし孤立しているだけで削除しない。

次を判断する。

- 他 Pattern から関連付けるべきか
- 不要な重複か
- 意図的に独立しているか

---

## 壊れたリンク

Markdown 内で参照しているファイルが存在するか確認する。

例:

```text
関連: incident_old.md
```

対象ファイルが存在しなければ Lint エラー。

---

## provenance の存在確認

Pattern が参照する Raw ファイルが実在するか確認する。

次のような状態を検出する。

```text
source: /knowledge/raw/foo.md
```

しかし、

```text
foo.md が存在しない
```

場合。

これは高優先度で報告する。

---

## 重複 Ingest セクション

同一 Pattern ページ内に同一 Raw パスの provenance が複数出現する状態を検出する。

create_pattern.py はクラッシュ復帰を行わないため（2026-10-12 決定）、クラッシュ後再実行で同一内容の `Ingest <日時>` セクションが重複して書き込まれることがある。

- 検出: ページ内で同一 Raw パスの Ingest セクションが複数、かつ内容が実質同一なら重複候補（WARNING）
- 削除はユーザー承認後に実行（Pattern 削除・統合は自動変更しない対象）

---

## Pattern 種別

ファイル名や frontmatter に指定された種別が、許可されたものか確認する。

例:

```text
decision-pattern
incident-pattern
experiment-pattern
```

表記揺れ:

```text
decision
decision_pattern
DecisionPattern
```

などを検出する。

---

# Phase 3. 重複候補を抽出する

全ファイルを総当たり比較しない。

候補を次の方法で絞る。

## ファイル名

例:

```text
incident_wails_ime.md
incident_linux_wails_ime.md
```

似た名前なら重複候補。

---

## summary

`index.db` の summary に同じ重要語が多く含まれる Pattern を候補にする。

例:

```text
Wails
Linux
IME
WebKitGTK
```

が両方に多く含まれている場合。

---

## 技術・固有名詞

同じ製品名、エラー、設定値などを扱う Pattern を集める。

例:

```text
Strata
parallel
expert cache
```

を含むファイル群だけ比較する。

---

# Phase 4. 重複を意味的に確認する

候補になったファイルだけ本文を読む。

次を判断する。

### 同一知識

結論、条件、対策がほぼ同じ。

→ 統合候補。

### 同じテーマだが別条件

例:

```text
RTX 3090 / RAM 32GB
```

と、

```text
RTX 5090 / RAM 128GB
```

など。

→ 原則として重複扱いしない。

必要なら1つの Pattern に条件別事例として統合する。

### 同じ症状だが原因が異なる

→ 別 Pattern のままとする。

---

# Phase 5. 矛盾候補を抽出する

全 Pattern 同士を比較しない。

まず同じ対象を扱う Pattern 群を作る。

例:

```text
Strata
Wails
OpenCode
SQLite
Qwen
```

など。

そのグループ内だけ比較する。

確認するのは主に次。

- 結論が逆
- 推奨設定が異なる
- 原因説明が異なる
- 対策が異なる
- 適用条件が重なっているのに結論が違う

---

# 矛盾の判定

例:

Pattern A:

```text
parallel=2 を推奨
```

Pattern B:

```text
parallel=1 を推奨
```

だけでは矛盾と確定しない。

まず条件を見る。

```text
GPU
RAM
モデル
Strata バージョン
入力サイズ
評価指標
```

条件が異なれば両方正しい可能性がある。

条件がほぼ同一なのに結論が異なる場合のみ矛盾候補とする。

Lint では勝手に片方を正しいと決めない。

---

# Phase 6. Raw との整合性

すべての Pattern について Raw 全文を再確認する必要はない。

次の場合のみ Raw へ降りる。

- Pattern 同士が矛盾する
- Pattern の主張が強すぎる
- provenance が怪しい
- 実測値の確認が必要
- 結論の根拠が不明
- 新しい Raw が既存 Pattern と一致しない

Raw と Pattern が異なる場合は、

```text
Pattern が一般化した結果なのか
単純な誤りなのか
Raw が古いのか
```

を区別する。

---

# Phase 7. 古い前提を検査する

「古いファイル」自体は問題ではない。

問題なのは、**現在成立しない前提に依存していること**。

例えば:

```text
Ubuntu 24.04 固有
Strata 0.1.x 固有
旧 API 固有
修正済み upstream bug
```

など。

古い可能性がある Pattern は次を確認する。

- バージョンが固定されているか
- 再検討条件が満たされていないか
- 新しい Pattern / Raw が存在しないか
- upstream の仕様変更を前提にしていないか

古いだけで削除しない。

必要なら、

```text
再検証候補
```

として報告する。

---

# Phase 8. 対策の有効性

incident-pattern などについて、

```text
この対策は本当に効いているか
```

を確認する。

次を探す。

- 対策後にも同じ問題が再発している
- 新しい Raw で同じ失敗が記録されている
- 回避策が恒久対策として書かれている
- 対策の適用条件が書かれていない

再発している場合は、

```text
対策が不十分
条件不足
原因誤認
```

の候補として報告する。

---

# Phase 9. Wiki と Skill / AGENTS.md の整合性

Wiki に蓄積された知識と、現在の開発ルールが矛盾していないか確認する。

対象例:

```text
AGENTS.md
knowledge-base/SKILL.md
その他 Skill
```

ただし Wiki の知識が常に Skill より優先されるわけではない。

矛盾を発見した場合は、

```text
Wiki を更新すべきか
Skill を更新すべきか
条件の違いか
```

を判断候補として提示する。

Skill / AGENTS.md を自動変更しない。

---

# 100ファイルの場合の実行例

Wiki に100ファイルある場合:

```text
100 files
   ↓
構造検査
   ↓
100 files
   ↓
ファイル名・summary・キーワードでグループ化
   ↓
重複候補 12組
矛盾候補 7組
孤立 4件
provenance異常 3件
   ↓
候補だけ本文確認
   ↓
Raw確認が必要 5件
   ↓
Lint結果
```

つまり、

```text
100ファイルを全部詳細比較
```

ではなく、

```text
100ファイルを浅く検査
↓
怪しい10〜30件だけ深く検査
```

とする。

---

# Lint の出力

Lint は問題を修正することより、まず候補を分類して提示する。

例:

```text
Lint summary

ERROR
- provenance 参照先なし: 2
- 壊れた Wiki link: 1

WARNING
- 重複候補: 4組
- 矛盾候補: 2組
- 古い前提の可能性: 3
- 対策再発: 1

INFO
- 孤立ページ: 2
- Promote候補: 1
```

各項目には、

```text
対象ファイル
理由
関連ファイル
確認すべき点
推奨アクション
```

を付ける。

---

# 深刻度

Lint の問題自体は次の3段階で十分。

## ERROR

知識として明確に壊れている。

例:

- provenance の参照先がない
- 壊れたリンク
- 不正な構造
- 存在しないファイルを根拠としている

## WARNING

人間または AI の判断が必要。

例:

- 重複候補
- 矛盾候補
- 古い前提
- 対策再発
- 過度な一般化

## INFO

改善候補。

例:

- 孤立ページ
- Pattern 間リンク追加候補
- Promote候補
- 命名揺れ

---

# Lint で自動修正してよいもの

意味を変えないものだけ自動修正してよい。

例:

- 明白なリンクパス修正
- log.md の機械的な追記
- フォーマットの正規化

ただし、判断を伴う場合は修正候補を提示するだけにする。

次は自動変更しない。

- Pattern の統合
- 結論変更
- 矛盾解消
- provenance の捏造
- Pattern 削除
- Skill / AGENTS.md への Promote

---

# 完了条件

全体 Lint は次を確認したら完了とする。

- 構造エラーを検査した
- 孤立ページを検査した
- provenance を検査した
- 重複 Ingest セクションを検査した
- 重複候補を抽出した
- 矛盾候補を抽出した
- 古い前提の候補を抽出した
- 対策再発を確認した
- Skill / AGENTS.md との矛盾候補を確認した
- Promote候補を確認した
- 問題を ERROR / WARNING / INFO に分類した

すべての Wiki を毎回 LLM で全文比較することは完了条件に含めない。
