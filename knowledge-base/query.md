# Query — 知識を検索・利用する

ローカル Markdown 知識ベースから、現在の質問・設計・実装・調査に必要な既存知識を探して利用する。

作業開始時に Raw を無差別に読まない。

まず Wiki Pattern と `index.db` を使って候補を絞り、必要な場合のみ Raw まで遡る。

---

# 基本原則

`index.db` は知識そのものではなく、**読むべき Markdown を発見するための検索索引**である。

正本は Markdown であり、`documents.summary` は LLM が生成した検索補助情報にすぎない。

- `summary` は候補ファイルを見つけるために使う
- `summary` だけを根拠に事実判断しない
- 重要な判断では候補となった Markdown 原文を読む
- 全文書を読むのではなく、検索によって読む対象を絞る
- 検索結果が弱ければ検索語を変えて再検索する
- Wiki Pattern を優先して確認し、必要な場合のみ Raw まで遡る

---

# いつ Query するか

次のような場合に使用する。

- 新しい設計や実装方針を決める前
- 不具合調査や性能改善を始める前
- 過去の失敗、制約、実測、回避策が参考になりそうなとき
- 既存の設計判断を変更・置換する前
- 過去に扱った可能性がある技術を再度使うとき
- 関連する Markdown や Pattern を探したいとき
- 「以前」「前に」「過去に」扱った内容を確認したいとき
- 同じ調査や設計ミスを繰り返す可能性があるとき

単純な一般知識だけで十分な場合は不要に Query しない。

---

# 基本順序

```text
質問・開発タスク
    ↓
検索意図を整理
    ↓
Wiki / index.db で候補を検索
    ↓
関連 Wiki Pattern
    ↓
必要な場合のみ Raw source
    ↓
現在の判断・設計・回答に利用
```

入口は `index.db` である。wiki 全ページは documents に登録済みで、`SELECT path, summary FROM documents WHERE path LIKE '%/wiki/%'` で一覧と一言説明が得られる。

---

# Raw に降りる条件

次の場合は Wiki Pattern だけで判断せず Raw まで遡る。

- Wiki の記述に疑問がある
- 根拠を確認したい
- 正確な実測値やログが必要
- Wiki が過度に一般化されている
- 矛盾が見つかった
- 新しい事例と既存ルールが合わない
- 正確な時系列が必要
- 適用範囲が今回の条件に合うか不明

---

# 検索語の作り方

要求をそのまま1語検索しない。

検索前に3〜8語程度の検索語を作る。

候補には次を含める。

- 固有名詞
- 製品名
- プロジェクト名
- 技術名
- 英語表記
- 日本語表記
- 略称
- 同義語
- 関連する専門用語

例:

```text
StrataでRAMからexpertをGPUに載せ替える話
```

なら、

```text
Strata
expert
expert cache
RAM
GPU
resident experts
low ram
MoE
```

などを候補にする。

---

# 検索対象

`documents.path` と `documents.summary` の両方を検索する。

ファイル名・ディレクトリ名も重要な検索情報なので、summary だけを検索しない。

ファイル名そのものに検索語が含まれる場合は強い候補として扱う。

---

# 検索結果の扱い

検索結果は「回答」ではなく「候補」である。

summary には次の問題があり得る。

- 情報の省略
- 誤解
- 誤った一般化
- 原文にない表現
- 時系列の欠落
- LLM による幻覚

そのため、

```text
検索
↓
候補抽出
↓
Pattern / 原文確認
↓
判断
```

の順で利用する。

summary の内容だけで判断しない。

---

# ランキング

新しさより関連度を優先する。

基本的な優先順位:

1. path に固有名詞や検索対象が直接含まれる
2. summary に複数の重要語が含まれる
3. 完全なフレーズや強い関連語が一致する
4. 単一語だけ一致する
5. 同程度なら新しい文書を優先する

---

# 読む件数

目安:

```text
検索候補:
10〜20件程度

実際に読む Pattern / 原文:
3〜5件程度
```

1〜2件に明確に絞れる場合は、それ以上読む必要はない。

---

# 検索ワークフロー

## 1. 検索意図を整理する

次を抽出する。

- 主題
- 固有名詞
- 関連技術
- 別表記
- 検索に使えそうな語

## 2. Wiki を確認する

関連 Pattern から直接到達できる場合はそれを使う。

## 3. index.db で候補を探す

Wiki だけで不足する場合、`index.db` を使う。

この環境で `sqlite3` CLI がない場合は Python 標準ライブラリ `sqlite3` を使う。

検索では `path` と `summary` を両方評価し、関連度を優先して候補を絞る。

## 4. 有力候補を選ぶ

次を見る。

- path
- summary
- 一致した検索語
- 更新日時
- 現在の質問・作業との直接的な関係
- Wiki Pattern か Raw か

## 5. Pattern / 原文を読む

Wiki Pattern を優先して読み、必要なら Raw まで遡る。

最終判断は Markdown 本文に基づく。

summary と原文が矛盾する場合は原文を優先する。

## 6. 必要なら再検索する

原文を読んだ結果、

- 別の用語が重要だと分かった
- 別ファイルへの言及があった
- 情報が不足していた

場合は、その語を使って再検索する。

通常は2〜3回程度まででよい。

---

# 検索失敗時

0件でもすぐに「存在しない」と判断しない。

次を試す。

1. 日本語と英語を切り替える
2. 製品名・固有名詞だけで検索する
3. 略称を試す
4. 上位概念・下位概念に変える
5. path だけを検索する
6. summary 未生成文書を考慮する
7. 候補文書から得た専門用語で再検索する

---

# summary の扱い

`summary` は全文代替ではなく、検索 Recall を高めるためのデータである。

summary が空の場合:

```text
summary = ''
```

path 検索や原文確認で補う。

summary が古い場合:

```text
modified_at > summary_at
```

候補発見には利用してよいが、現在の内容確認では原文を読む。

ファイルが移動した場合（同名・同一内容）、同期時に `hash` とファイル名の一致で既存行の要約が再利用され、`summary_at` は新しい `modified_at` に設定される（内容同一のため再生成されない）。改名した場合は再利用されない。

---

# Ingest 状態の扱い

`documents.ingest_status` は内容確認状態（`''`=未確認 / `patterned`=wiki の Pattern 化した / `not_needed`=pattern化不要）。

未確認ファイルの一覧:

```sql
SELECT path, summary FROM documents WHERE ingest_status = '' ORDER BY modified_at DESC;
```

ファイル編集では保持され、同名移動では引き継がれる。設定・変更の手順は `ingest.md` の「Ingest フラグ」。

---

# 検索方式の優先順位

現時点では、単純で保守しやすい方式を優先する。

1. `index.db`
2. `rg`
3. 必要なら SQLite FTS5
4. 規模が増え文字列検索で不足した場合のみ semantic search / RAG

ベクトル DB は chunking、embedding model、reindex、retrieval tuning、embedding version migration などの運用を増やす。

必要になるまでは知識管理システム自身を複雑化させない。

---

# Query の完了条件

Query は次を満たした時点で完了とする。

- 関連する既存 Pattern / Raw が十分に確認されている
- summary だけで事実判断していない
- 現在の条件に適用できる知識か確認している
- 必要なら provenance から Raw まで遡っている
- 過去の判断を無条件に踏襲していない
- 現在の設計・調査・回答に必要な知識だけを取得している

目的は、

> **過去の知識を最小限の読み込みで発見し、現在の判断に再利用すること。**

である。
