# 設計判断 Pattern

## 結論
採用する設計・方式・方針を簡潔に記述する。

## 背景
何を実現したかったか。
なぜ設計判断が必要になったか。

## 条件・制約
判断に影響した条件だけを書く。

- OS / 実行環境:
- ハードウェア:
- ソフトウェア / バージョン:
- 性能要件:
- 互換性:
- 運用上の制約:
- その他:

## 候補
比較した案を列挙する。

- 案A:
- 案B:
- 案C:

## 採用理由
なぜ採用案を選んだか。
他の条件では結論が変わる場合、その条件も記述する。

## 却下した案
将来再検討しそうな案について、却下理由を残す。

- 案A:
  - 却下理由:
- 案C:
  - 却下理由:

## 根拠
判断を支えた実測、検証結果、Raw、外部資料などを記載する。
推測と確認済み事実を区別する。

## 適用範囲
この判断が成立する範囲を記述する。
単一環境で確認した内容を一般化しすぎない。

## 再検討条件
どの条件が変わったら、この判断を見直すべきか。

例:
- 要件が変わった場合
- ハードウェア構成が変わった場合
- upstream の制約が解消された場合
- ライブラリのメジャーバージョンが変わった場合
